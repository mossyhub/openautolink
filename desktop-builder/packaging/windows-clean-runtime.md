# Windows clean-runtime native probe (CI only)

This is a destructive **disposable GitHub-hosted Windows Server 2022** test.
Never run it on a user's computer, a self-hosted runner, or a persistent VM.
The independent PowerShell guard also requires `runneradmin`, inbox 64-bit
PowerShell 5.1, administrator membership, `ImageOS=win22`, and explicit
`disposable-ci-only-not-user-consent` authorization. No production acceptance
switch is added. No Windows security/UAC/PowerShell policy is modified.

## Maintainer run

Push the exact reviewed checkout to the explicitly authorized maintainer branch
`feat/desktop-personal-builder`; changes to the listed worker/bootstrap inputs
trigger the dedicated hosted job even before the new workflow reaches default.
This branch-push path is test-environment authorization, not recipient assent.
Alternatively, once available for dispatch, run
`qualify-windows-clean-runtime.yml` on the reviewed ref with
`authorize_disposable_test_acceptance=true`. The job freezes its own **AAB-only** private candidate. It does not build Android
source or upload any executable. The ordinary coverage gate is unchanged.

The optional hook runs inside `windows_setup.probe_candidate`, while the exact
private outer executable and extracted, hash-verified inner builder still
exist. Source snapshots include both worker files and the dedicated workflow.
No native claim may be made from Linux parser/unit fixtures.

## Timeout and recovery ownership

An independent inbox PowerShell supervisor owns scenario teardown and recovery.
Mutation launchers start suspended in kill-on-close Windows Jobs, so descendants
remain owned even after a launcher exits. Recovery runs only after owned-tree
termination and MSI quiescence are confirmed; otherwise the test fails and the
VM must be discarded. Process evidence counts only observed job-owned processes.

The scenario has an 840-second cooperative deadline and a 900-second supervisor
limit. Reserved teardown, MSI-drain, recovery and final-teardown waits bring the
bounded supervisor budget to 1260 seconds. The Python controller waits 1350
seconds and records a separate failure/stop signal on timeout rather than killing
the recovery supervisor. Admission requires 1470 seconds of step time remaining.
These bounds are test safeguards, not evidence of native execution or recovery.

## Real sequence and evidence

1. Bind clean checkout/run identity, inner/source/outer/bootstrap/worker hashes.
   Verify the worker's source bytes against the embedded corresponding source.
2. Inventory both HKLM registry views and actual System32 VC14 DLLs/versions.
   Probe actual input desktop/session/UIAutomation **before removing anything**.
   Record noninteractive/session-zero/input-desktop denial as a failure, not a skip.
3. Preload inbox .NET/WMI/UIAutomation; cache the exact pinned Microsoft installer
   and verify SHA-256 plus Microsoft's valid Authenticode signature. Hold its
   read-sharing lock through recovery. Python is not used during removal/install.
4. Uninstall only registered Microsoft VC14 **x64** bundles and minimum/additional
   MSI products. No registry/DLL deletion and no Win32_Product repair scan.
   Require both registry views genuinely empty and all three actual runtime DLLs
   absent. Stale registration or a too-old/present DLL fails closed.
5. Corrupt-file negative control calls the original production hash function.
   This is explicitly fault-injection **pre-execution integrity** evidence, not
   a real installer/network failure, not a changed production download source.
6. Launch the actual outer bootstrap and click **No** at its download prompt.
   Require nonzero exit, no installer/builder process starts, and unchanged
   genuine runtime absence. Dismiss the real error dialogs.
7. Launch again, permit download, observe Microsoft's real unchecked license
   checkbox, then **Cancel** its installer (confirm only the owned Microsoft
   dialog if necessary). Require observed real installer process start, nonzero
   outer exit, no builder process start, and runtime still absent.
8. Launch again; accept the test-environment installer terms using UIAutomation,
   click Install, observe Setup Successful and Close. Accept the frozen builder's
   own Microsoft-only terms **for the disposable test account only**. Require
   the actual normal frozen AAB wizard (Application ID, Continue, signed Android
   App Bundle text), real builder process starts, installed registry and DLL
   versions, and successful outer exit after closing the wizard.
9. Rehash unchanged candidate bytes. Controller validates all report invariants
   and image digests before writing a separate bounded verification receipt.

All screenshots are bounded crops of owned test windows, not desktop captures.
The wizard's managed-folder text is redacted; no credentials are supplied, no
signing identity is generated by a build, and no personal account is used.
Exports are enumerated JSON and six PNG paths only. WMI events and arbitrary
UI text/exception strings/paths/environment/installer logs are never exported.

The elevated hosted account cannot prove a real user's secure-desktop UAC
acceptance/cancellation or restart-required behavior. Those are explicitly
`not-tested`; do not relabel them as passed. An observed timeout alone proves
only an expected-control timeout, not a diagnosis that UAC is unsupported.

On failure after removal, inbox PowerShell attempts **separately labelled,
non-qualifying** recovery from the cached signed/hash-pinned installer. Its
quiet flags are confined to ephemeral uninstall/recovery, never the production
bootstrap or the accepted installation scenario. If recovery cannot complete,
discard the ephemeral VM; do not turn that cleanup into installation evidence.

## Parent evidence-to-gate integration (deliberately not implemented here)

Keep `WINDOWS_BOOTSTRAP_UNVALIDATED` until a real successful native run is
reviewed. `coverage_windows_ci.py` is untouched. A successful dedicated workflow
means only its clean-runtime evidence controller passed; the ordinary private
packager may still fail at the intentionally unchanged distribution gate.

Verify the receipt's report digest, run/attempt/checkout identity and exact
source/candidate/outer/bootstrap/worker hashes against the same run's private
candidate evidence. Inspect every screenshot for actual readable UI. Reject
failure/partial reports, missing images, old source hashes, synthetic unit
fixtures, recovery-only installations, offscreen UI and unverified report-only
success labels. Decide explicitly whether this scoped absent→interactive
install→actual-wizard evidence closes the intended gate; do not imply it tested
UAC decline, reboot, transport failures, or real-user consent.

## If hosted desktop automation is unavailable

Retain `windows-clean-install.json` with the exact bounded `phase`,
`failureCode`, session ID, interactive flag, input-desktop result and Win32
error. `NO_INTERACTIVE_SESSION`, `INPUT_DESKTOP_UNAVAILABLE`,
`SECURE_OR_NONDEFAULT_DESKTOP`, and `UIAUTOMATION_UNAVAILABLE` are distinct.
Do not disable secure desktop, enable autologon, RDP into the user's computer,
spoof clean state, skip the scenario, or clear the gate.

The remaining manual acceptance protocol is the same numbered sequence above,
on a separately approved disposable interactive Windows VM (outside this
worker's hosted-only guard): a human records both registry views and System32
versions before/after, confirms genuine absence, performs No/Cancel/Accept,
records installer signature/hash, and captures only sanitized test-window
screenshots plus exact candidate/source identity. Label this manual evidence
separately; do not claim a hosted CI pass. A real UAC/reboot claim requires its
own explicit manual observation. Never perform it on the recipient's host.
