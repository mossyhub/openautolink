# Ordinary first-controller enrollment: integration hooks

## Finding (supersedes missing-binding premise)

Apple WWDC17 session 717 describes native Bluetooth UI selection, Bluetooth Secure Simple Pairing, iAP2, iPhone Enable Wireless CarPlay consent, native CarPlay consent when selection came through general Bluetooth menus, Wi-Fi credentials after consent, discovery and session start. A CarPlay-specific selection already communicates that choice. WWDC23 session 10150 describes the preferred iAP2 IP/port exchange (iOS14+) replacing Bonjour. Neither public description supplies a selected-phone Ed25519 cross-transport binding. Pinned DiPlay's fixed-code SRP then Ed25519 PairSetup and separate MFiSAP/iAP2 accessory authentication implement an interoperable trust-on-first-enrollment path. The previous demand for an additional cryptographic BT→controller-key handoff was OAL's extra threat model, NOT a demonstrated CarPlay protocol requirement.

This does NOT prove that a licensed private spec has no additional mechanisms. It means the inspected interoperable sources do not require the invented one. No tokens, crypto substitutes, or MFi/PairVerify bypass are justified.

## APIs implemented by enrollment owner (runtime owner must wire)

`CarPlayPeerAdmission(selection, startupControllers, trustedOnly = true, enrollmentWindowMillis = 120_000)` enables first enrollment **only when startupControllers is empty**. Default window=0 retains trusted reconnect and fails empty-store admission. Window is bounded 0..120000 ms, monotonic, starts at construction; this timeout is OAL hardening, not an Apple duration. One live pre-auth owner, 32 attempts, exact interface/family/scope/address remain.

1. Runtime owner should construct the first-enrollment admission only after exact selected bootstrap identification and genuine receiver MFi success, with existing OAL opt-in/connection permissions and sourced native/iPhone consent. Do not promote a generic bond inventory to selected-phone authority. Carry exact runtime lifetime and revoke on cancellation/selection change. Do not disable MFi or add an OAL pairing UI without a source-backed necessity.
2. Remove the universal empty-store/binding blocker from `OalCarPlayRuntime` and `ProjectionReceiver` **only for this explicitly authorized mode**. Keep `trustedOnly=true`; do NOT simply flip it false.
3. Construct the exact `AirPlaySession`, claim it in admission before starting its control worker; use `admission.allowsPairSetup(session)` as its initial allowPairSetup flag. Parent needs an optional `saveController` callback on AirPlaySession that is passed into its `PairSetup(identity, pairings, saveController)` constructor.
4. That callback must call `admission.persistEnrollment(session, id, key, persistence.pairings)` and return its Boolean. It commits under the exact owner/retirement fence, only after genuine SRP + Ed25519 M5 proof in PairSetup. PairSetup returns TLV authentication error on false/exception; never saves on denial. It verifies the committed store contains the proved key before returning M6 success. Do not fall back to plain save when a production callback rejects.
5. `onControlAuthenticated` must accept both startup-trusted and the **committed** first controller through `admission.authenticate(session, session.controllerId)`, called only after real PairVerify. Remove the extra immutable `session.controllerId in trustedControllers` check for scoped enrollment, since that snapshot is empty at first install. PairSetup alone cannot create media readiness. Keep actual PairVerify encrypted-control transition and ancillary socket binding unchanged.
6. `admission.retire()` must be called on revoke/cancellation as well as close; it linearizes against durable commit. Cancellation that wins the fence rejects late M5; commit that wins first remains persisted but grants no post-retirement media. Do not wait for admission under an unrelated lock that the persistence callback needs. Continue retaining PairingPersistence ownership until all control workers stop.
7. Once committed, PairSetup cannot run again in this admission owner, even after control disconnect. A new connection in the same owner may PairVerify the committed key; a successor uses fresh persisted startup trust. Existing trust ignores enrollment window for media lifetime; no bench lifetime timer.
8. Applies to scoped unknown IPv6 AP ingress and explicit selected/manual IPv4 paths; never wildcard enrollment merely because an IP override is supplied. Existing legacy lab constructor behavior remains separate.

## Risk accepted, not silently claimed solved

Fixed-code SRP proves a candidate's presented key, not selected Bluetooth phone identity. MFiSAP/iAP2 prove the accessory to the phone. A reachable rogue client that knows the fixed code and shares access to the AP can race or deny first enrollment; one candidate and a deadline reduce exposure but do not solve it. Native selection/permission/consent and a protected AP are the deployment authorization boundary. A family AP with other occupants is not an isolated channel. Persisting only the first proved controller prevents subsequent automatic takeover, not the initial race. Strict selected-phone cryptographic assurance remains an optional stronger product policy, not the default protocol interoperability requirement.
